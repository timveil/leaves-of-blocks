# Logging

**Log through `BuildConfiguration`, never `print`.**

The app's logging goes to the unified logging system via a single `os.Logger`
in `Services/Configuration/BuildConfiguration.swift`, tagged with the bundle
identifier as its subsystem so Console.app can filter on it.

## Why not `print`

`print` writes to stdout, which on a device nobody is reading. It has no level,
so a diagnostic and a failure look identical; no subsystem or category, so it
cannot be filtered; and it is not stripped from release builds, so it costs
string interpolation on every call in shipping code for output no one sees.

`os.Logger` is filterable and level-aware, and the release floor is set for
you: `currentLogLevel` is `.debug` in debug builds and `.warning` in release.
Levels run `.verbose`, `.debug`, `.info` (the default), `.warning`, `.error`,
`.none`.

**Filtered does not mean free.** `log(_:level:)` takes a `String`, so the
message is built at the call site before the level guard ever runs — unlike
`os.Logger`'s own interpolation, which defers the work. A `.verbose` call in a
hot path still pays for its interpolation in a release build:

```swift
// Interpolates on every frame even though release never emits .verbose
BuildConfiguration.log("grid \(describe(grid))", level: .verbose)

// Guard the call site when the message is expensive and the level is low.
// LogLevel is Int-raw but not Comparable, so compare rawValue as log() does.
if BuildConfiguration.LogLevel.verbose.rawValue
    >= BuildConfiguration.currentLogLevel.rawValue {
    BuildConfiguration.log("grid \(describe(grid))", level: .verbose)
}
```

For ordinary messages this does not matter. It matters in the game loop.

`logSolvability` is a `BuildConfiguration` extension declared in
`Logic/Game/BlockGenerator.swift`. It prefixes `[SOLVABILITY]` and calls `log`
— a tagging convention for block-generation diagnostics, not a separate
`os.Logger` category. The logger's category is `"app"` throughout.

## Wrong

```swift
print("Failed to save game record: \(error)")
```

## Right

```swift
BuildConfiguration.log("Failed to save game record: \(error)", level: .error)
```

## The exception: previews

`#Preview` blocks may use `print` for action closures. A preview needs
*something* callable, the code never ships, and routing preview taps through the
app's logger adds noise to Console for no benefit:

```swift
#Preview {
    FullWidthActionButton(title: "Primary Button") {
        print("Primary tapped")   // fine — preview only
    }
}
```

This is the only sanctioned exception, and it is exactly where the rule erodes:
a `print` written in a preview gets copied into a view.

## Privacy

Messages are emitted with `privacy: .public` where the value is safe to record
— note the `\(public:)` shorthand in `BuildConfiguration`'s own doc comment is
loose; the implementation uses `\(message, privacy: .public)`.
Be deliberate: the app collects almost nothing, and its logs should not become
the place that changes. Never log a Game Center player identifier or anything
that could identify a device.

## Current state

Zero `print` calls in app code, and no `os_log` or `debugPrint` anywhere.

`NSLog` does appear, in `LeavesOfBlocksUITests/SnapshotHelper.swift` — fastlane's
vendored screenshot helper, which is third-party code regenerated by the tool
and not ours to restyle. This convention covers the app target and the code we
write; leave vendored files alone.

It records a practice that already holds rather than correcting a lapse —
written down because it is currently upheld by one file and one habit, and the
previews exception is the detail that will go first.
